# Per-Task Execution Checklist

목적: 각 task 파일 실행 후 동일한 형식으로 보고하도록 체크리스트를 정의한다.

---

## 작업 전 확인

- [ ] task 파일의 **변경 범위** 섹션을 먼저 읽는다
- [ ] **수정 허용 파일** 목록을 확인한다
- [ ] **수정 금지 파일** 목록을 확인한다
- [ ] 현재 파일 구조가 task의 전제와 일치하는지 확인한다
- [ ] public API 변경 가능성을 확인한다
- [ ] 관련 기존 함수/클래스와 테스트 존재 여부를 확인한다

## 구현 범위 확인

- [ ] task의 **구현 지시** 순서를 그대로 따른다
- [ ] 허용 파일 외 파일을 수정하지 않는다
- [ ] 임의 개선/정리를 추가하지 않는다
- [ ] 투자 판단 로직(`api/strategy/`)을 변경하지 않는다
- [ ] shim 생성 없이 진행 가능한지 확인한다

## 구현 중 중단 조건

다음 상황 발생 시 즉시 중단하고 디버깅 보고서를 작성한다:
- 지정 파일이 존재하지 않거나 예상 구조와 다를 때
- 변경 범위가 다른 레이어로 확산될 때
- 비즈니스 규칙 판단이 필요할 때
- shim 없이 진행이 불가능할 때
- DB schema 의미 변경이 필요할 때

## 테스트 확인

- [ ] task에 지정된 **실행 명령**을 그대로 실행한다
- [ ] 지정된 테스트 파일이 통과하는지 확인한다
- [ ] 기존 테스트가 regression 없이 통과하는지 확인한다

## 보고 형식

작업 완료 후 반드시 다음 형식으로 보고한다:

```text
변경 파일: <수정한 파일 목록>
추가 파일: <새로 생성한 파일 목록>
삭제 파일: <삭제한 파일 목록>
실행 테스트: <실행한 명령>
실패 테스트: <실패한 테스트 없음 또는 실패 내용>
남은 리스크: <없음 또는 구체적 리스크>
```

## Phase 완료 보고 형식

```text

완료한 task:
- <task 파일명>

수정/생성/삭제 파일:
- <path>

실행한 검증:
- <command>

결과:
- 성공 / 실패

남은 이슈:
- 없음 또는 구체적 이슈

다음 phase:
- <다음 phase 파일명>
```

```text
수정한 파일: <파일 목록>
실행한 명령: <명령>
실패 로그 핵심: <로그 발췌>
원인 추정: <원인>
최소 수정안: <수정 방향>
사용자 확인이 필요한 결정: <없음 또는 결정 사항>
```
